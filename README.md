# ManageEngine ServiceDesk Plus Connector for midPoint

A [ConnId](https://docs.evolveum.com/connectors/connid/1.x/) connector that allows
[Evolveum midPoint](https://evolveum.com/midpoint/) to manage user accounts in
**ManageEngine ServiceDesk Plus** (SDP) through the SDP REST API v3 (`/api/v3/users`).

midPoint can create, read, update and delete SDP users (requesters and technicians) and reconcile them with
midPoint users. The connector is designed for on-premise installations that authenticate with a technician API key.

## Status: Beta

This connector has been successfully tested in a local/staging environment, covering the full identity lifecycle (Create, Read, Update, Delete) against ServiceDesk Plus API v3. However, it has not yet been deployed in a large-scale production environment. Community testing, feedback, and contributions are highly welcome.

## Compatibility

| Component | Version |
|---|---|
| Connector | 1.1.1 |
| ConnId framework | 1.5.0.0 |
| Java | 17 or later |
| midPoint | 4.9 or later (the sample resource uses object types with `delineation`, `synchronization` and the items correlator). Tested with 4.9.1 |
| ManageEngine ServiceDesk Plus | On-premise build 11000 or later (the `/api/v3/users` endpoint). Tested with 16.0 (build 16010) |

## Capabilities and limitations

| Capability | Supported | Implementation |
|---|---|---|
| Schema discovery | Yes | Static schema with one object class: `__ACCOUNT__` |
| Test connection | Yes | Requests one row of `GET /api/v3/users` |
| Search | Yes | Paged `GET /api/v3/users`, see [Search behaviour](#search-behaviour) |
| Create | Yes | `POST /api/v3/users` |
| Update | Yes | `PUT /api/v3/users/{id}` |
| Delete | Yes | `DELETE /api/v3/users/{id}` |
| Live synchronization | No | Use reconciliation |
| Groups, roles, entitlements | No | |
| Connection pooling | Yes | `PoolableConnector`; the liveness check repeats the connection test |

Only the `__ACCOUNT__` object class is supported.

### Search behaviour

| Filter | How it is executed |
|---|---|
| Equals on `__UID__` | Direct `GET /api/v3/users/{id}`. An unknown id returns an empty result |
| Equals on `email` | Evaluated by ServiceDesk Plus (`list_info.search_fields`) |
| Anything else, or no filter | All users are listed page by page, sorted by `name`, and filtered by the connector in memory |

## Resource schema

`__UID__` is the numeric SDP user `id`. It is unique and immutable, and midPoint uses it as the primary identifier.

`__NAME__` is the SDP `name` field (the *display name*). It is the only field that ServiceDesk Plus requires for every
user, which is why it is used as the ConnId name. It is **not guaranteed to be unique** in SDP.

| Attribute | Type | SDP field | Access | Notes |
|---|---|---|---|---|
| `__UID__` | String | `id` | read | Generated by SDP |
| `__NAME__` | String | `name` | read, create, update | **Required** to create a user. Never cleared on update |
| `email` | String | `email_id` | read, create, update | Optional in SDP |
| `firstName` | String | `first_name` | read, create, update | |
| `lastName` | String | `last_name` | read, create, update | |
| `phone` | String | `phone` | read, create, update | |
| `mobile` | String | `mobile` | read, create, update | |
| `department` | String | `department.name` | read, create, update | Sent as `{"name": "<value>"}`. The department must already exist in SDP |
| `employeeId` | String | `employee_id` | read, create, update | Employee identifier stored in SDP |
| `isTechnician` | Boolean | `is_technician` | read | Read-only |

Replacing an optional attribute with no value clears it in SDP. Attributes that are not part of the update are left untouched.

## Installation

1. Build the connector (see [Building from source](#building-from-source)) or download a release jar.
2. Copy the jar into the `icf-connectors` directory of midPoint:

   ```bash
   cp target/connector-servicedeskplus-1.1.1.jar $MIDPOINT_HOME/icf-connectors/
   ```

3. Wait for midPoint to discover the connector, or restart midPoint. It appears in *Repository objects > Connector* as
   `ManageEngine ServiceDesk Plus Connector`.
4. Create the resource, for example by importing the [sample resource](#sample-resource).

### Upgrading

Remove the previous jar from `icf-connectors` so that only one version of the connector is registered, then restart
midPoint and update the version in the `connectorRef` filter of your resource.

If the new version exposes a different set of attributes than the one that created your existing shadows, midPoint fails
to load those shadows with an error such as `Unknown attribute '...' in 'ROTD(ACCOUNT:default...)'`. In that case delete the
shadows of the resource (*Repository objects > Shadow*, filtered by `resourceRef`) and run a reconciliation to relink the
accounts.

## Resource configuration

| Property | Type | Required | Default | Description |
|---|---|---|---|---|
| `baseUrl` | String | Yes | – | Base URL of ServiceDesk Plus with scheme and port, **without** `/api/v3`. Example: `https://sdp.example.com:8080`. Must start with `http://` or `https://`. Trailing slashes are removed |
| `authToken` | Guarded string | Yes | – | Technician API key. See [Authentication](#authentication) |
| `pageSize` | Integer | No | `100` | Users requested per page, from 1 to 100 |
| `timeoutSeconds` | Integer | No | `30` | Connect and read timeout of every HTTP call, from 1 to 300 |
| `trustAllCertificates` | Boolean | No | `false` | Disables TLS certificate and host name validation for this resource. Insecure, see [TLS / certificates](#tls--certificates) |

The configuration is validated when the connector is initialized. An invalid value raises an `IllegalArgumentException`
that names the offending property.

The configuration properties belong to an XML namespace that contains the connector **bundle name**:

```
http://midpoint.evolveum.com/xml/ns/public/connector/icf-1/bundle/<bundle name>/<connector class>
```

For this connector the bundle name is `com.rakkau.midpoint.servicedeskplus` (`ConnectorBundle-Name` in `pom.xml`) and the
class is `com.rakkau.midpoint.servicedeskplus.ServiceDeskPlusConnector`. If you change either, update the `cfg` namespace of
your resource. The exact value is shown in the `namespace` property of the connector object in midPoint. A mismatch makes the
resource import fail with a schema error.

Minimal configuration fragment:

```xml
<connectorConfiguration xmlns:icfc="http://midpoint.evolveum.com/xml/ns/public/connector/icf-1/connector-schema-3"
                        xsi:type="c:ConnectorConfigurationType">
    <icfc:configurationProperties
            xmlns:cfg="http://midpoint.evolveum.com/xml/ns/public/connector/icf-1/bundle/com.rakkau.midpoint.servicedeskplus/com.rakkau.midpoint.servicedeskplus.ServiceDeskPlusConnector">
        <cfg:baseUrl>https://sdp.example.com:8080</cfg:baseUrl>
        <cfg:authToken>
            <t:clearValue>YOUR_API_KEY</t:clearValue>
        </cfg:authToken>
        <cfg:pageSize>100</cfg:pageSize>
        <cfg:timeoutSeconds>30</cfg:timeoutSeconds>
        <cfg:trustAllCertificates>false</cfg:trustAllCertificates>
    </icfc:configurationProperties>
</connectorConfiguration>
```

midPoint encrypts `clearValue` when the resource is imported. Never commit a resource that contains a real key.

## Sample resource

[`samples/resource-servicedeskplus.xml`](samples/resource-servicedeskplus.xml) is a resource definition you can adapt.
It assumes that accounts are provisioned **from** midPoint, with a human-resources system as the authoritative source,
and that ServiceDesk Plus is only a target.

Before importing it:

- Replace `baseUrl` and `CHANGE_ME_API_TOKEN`.
- Make sure the `connectorVersion` in the `connectorRef` filter matches the installed connector (`1.1.1`). The filter selects
  the connector by class name and version, so it does not depend on the OID midPoint generated for it.
- Check the `cfg` namespace, see [Resource configuration](#resource-configuration).

Attribute mappings (focus type `UserType`):

| SDP attribute | Direction | midPoint source |
|---|---|---|
| `__NAME__` | outbound | `givenName` + space + `familyName`. Use `fullName` instead if your user template always computes it |
| `email` | outbound, plus a weak inbound used by the correlator | `emailAddress` |
| `firstName` | outbound | `givenName` |
| `lastName` | outbound | `familyName` |
| `phone` | outbound | `telephoneNumber` |
| `employeeId` | outbound | `employeeNumber` |

`department` is provided as a commented-out example. `mobile` and `isTechnician` are not mapped.

Correlation and synchronization:

| Item | Setting |
|---|---|
| Correlation | By `emailAddress`. SDP accounts without an e-mail cannot be correlated this way |
| `linked` | `synchronize` |
| `unlinked` | `link` |
| `deleted` | `unlink` |
| `unmatched` | **No reaction.** Accounts that exist only in ServiceDesk Plus are never imported as new midPoint users |

## Authentication

The connector authenticates with a technician API key that it sends in the `authtoken` header of every request, together with
`Accept: application/vnd.manageengine.sdp.v3+json`.

- Generate the key from the profile of a technician in ServiceDesk Plus (the exact menu depends on the SDP build).
- Use a dedicated technician whose role is limited to what the connector needs: view, add, edit and delete users.
- The key is stored as a confidential configuration property. Anyone who holds it can act as that technician.

OAuth 2.0, as used by ServiceDesk Plus Cloud, is not supported.

## TLS / certificates

By default the connector validates the server certificate against the trust store of the JVM that runs midPoint. If
ServiceDesk Plus uses a private CA or a self-signed certificate, import that certificate into the trust store used by
midPoint. This is the recommended setup everywhere except disposable test environments.

`trustAllCertificates=true` turns off certificate and host name validation for the connections opened by this resource. It
is applied per connection, and the JVM-wide HTTPS defaults are never modified, so other resources and components of midPoint
are not affected. The connector logs a warning at start-up when the option is enabled. Do not use it in production: the
connection becomes vulnerable to man-in-the-middle attacks and the API key can be intercepted.

The connector does not follow HTTP redirects, so that the API key is never sent to another location.

## Error handling

Failures are reported with ConnId exceptions so that midPoint can apply its consistency mechanisms.

| Situation | Exception |
|---|---|
| Invalid configuration value | `IllegalArgumentException` |
| Unsupported object class | `ConnectorException` |
| Missing `__NAME__` on create, unsupported attribute, multiple values for a single-valued attribute | `InvalidAttributeValueException` |
| HTTP 401 | `InvalidCredentialException` |
| HTTP 403 | `PermissionDeniedException` |
| HTTP 409, or an SDP message that indicates a duplicate | `AlreadyExistsException` |
| HTTP 404 on an operation on a specific user (read, update, delete) | `UnknownUidException` |
| HTTP 404 on the user list | `ConnectorException` (check `baseUrl`) |
| HTTP 400 or 422 on create, update or delete | `InvalidAttributeValueException` |
| Connection refused, timeout, unknown host, TLS failure, HTTP 502 / 503 / 504 | `ConnectionFailedException` |
| Other I/O errors | `ConnectorIOException` |
| HTTP redirect | `ConnectorException` |
| Any other HTTP error | `ConnectorException` |

Notes:

- On success SDP returns `response_status.status_code = 2000`. If an HTTP 2xx response carries a different status code, it is
  handled like an HTTP 400 error.
- A search by `__UID__` that finds nothing returns an empty result instead of an exception.
- The text of the SDP error (field and message) is appended to the exception message, which makes the cause visible in the
  midPoint operation result.
- Duplicate detection by message text is a heuristic that looks for phrases such as "already exists" or "must be unique".
  If your SDP build words these errors differently, they are reported as `InvalidAttributeValueException` instead.

## Logging and troubleshooting

The connector uses the ConnId logging API, so its messages go to the midPoint log. To see more detail, add a logger for the
package below in *Configuration > Logging* and set it to `DEBUG` (or `TRACE`):

```
com.rakkau.midpoint.servicedeskplus
```

| Level | Content |
|---|---|
| INFO | Id of the user after a create, update or delete |
| DEBUG / TRACE | HTTP method, path and status code of every call |
| WARN | `trustAllCertificates` is enabled |

The connector does not log the API key, request bodies, response bodies or query strings.

Common problems:

| Symptom | Likely cause |
|---|---|
| Resource import fails with a schema error | The `cfg` namespace of the resource does not match the bundle name of the registered connector, or two versions of the connector are registered |
| `Unknown attribute '...' in 'ROTD(ACCOUNT:default...)'` | Shadows created by a connector version with a different schema. See [Upgrading](#upgrading) |
| Test connection fails with a TLS or `PKIX` error | The certificate is not trusted by the JVM. Import the CA certificate |
| Test connection fails with "endpoint not found" or an HTTP 404 | Wrong `baseUrl` (path, port or scheme), or an SDP build without `/api/v3/users` |
| HTTP redirect error | `baseUrl` uses `http://` and the server redirects to `https://`, or a context path is missing |
| `InvalidCredentialException` / `PermissionDeniedException` | Key invalid or regenerated, or the technician has no permission on users |
| `UnknownUidException` on update or delete | The user was deleted directly in ServiceDesk Plus. Run a reconciliation |
| `InvalidAttributeValueException` on create | SDP rejected a value. The SDP message names the field |

## Known limitations

- `__NAME__` is the SDP display name and may not be unique. `__UID__` is the real identifier; use `email` or `employeeId` to
  match accounts, not the name.
- Users without an e-mail in SDP cannot be correlated by e-mail.
- Searches other than by `__UID__` or `email` read all users and filter them in memory. This is fine for small and medium
  installations and slower on large ones.
- Deleting a user that is both requester and technician, or that is referenced by open requests, may be refused by
  ServiceDesk Plus. The error is returned to midPoint.
- `isTechnician` is read-only. The technician role cannot be granted or removed through the connector.
- `department` is written by name and the department must already exist in ServiceDesk Plus.
- Live synchronization, groups and entitlements are not implemented.
- ServiceDesk Plus Cloud (OAuth 2.0 and the `/requesters` and `/technicians` endpoints) is not supported.

## Building from source

Requirements: JDK 17 or later and Apache Maven 3.8 or later.

```bash
mvn clean package
```

The build produces `target/connector-servicedeskplus-<version>.jar`, a single jar that contains the connector, its
dependencies (Jackson) and the ConnId manifest entries (`ConnectorBundle-Name`, `ConnectorBundle-Version` and
`ConnectorBundle-FrameworkVersion`). The ConnId framework itself is provided by midPoint.

Project layout:

```
src/main/java/com/rakkau/midpoint/servicedeskplus/
    ServiceDeskPlusConnector.java    connector operations and mapping to the SDP user model
    SdpHttpClient.java               HTTP calls, TLS policy and error mapping
    ServiceDeskConfiguration.java    configuration properties and validation
src/main/resources/com/rakkau/midpoint/servicedeskplus/
    Messages.properties              display names and help texts of the configuration properties
samples/
    resource-servicedeskplus.xml     sample midPoint resource
```

## Changelog

### 1.1.1

- `__NAME__` is the SDP display name (`name`), the only field SDP requires. `email` is an optional attribute.
- New attribute `employeeId`. `isTechnician` is now a read-only Boolean.
- Update and delete operations.
- Lookup by `__UID__` and by `email` is executed directly or by SDP instead of scanning all users.
- Specific ConnId exceptions instead of a generic `ConnectorException`.
- `trustAllCertificates` is applied per connection and no longer modifies JVM-wide defaults.
- API key stored as a guarded string. Request and response bodies are no longer logged.
- HTTP redirects are not followed.
- Sample resource: correlation by e-mail, no import of unmatched accounts.

### 1.0.1

- Initial version: test, schema, search and create.
